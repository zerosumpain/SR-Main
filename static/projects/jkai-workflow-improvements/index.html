2 · Delivered & committed

Commit 399b1aa (Wave 1, 11 items) and a follow-up commit (Wave 2a, #12). Each item's own tests passed in isolation at commit time. File references are from the implementing changes.

#1 — node_executions cross-run corruption done

Per-run UPDATEs were scoped by nodeId only; since nodeId is the static graph-node id reused on every run, completing one run overwrote the status/IO/cost/timestamps of all prior runs' executions of that node. Now scoped by and(eq(runId), eq(nodeId)), mirroring the already-correct engine-resume.ts.

src/lib/workflows/run-helpers.ts · src/lib/workflows/scheduler.ts · src/routes/api/workflows/[id]/run/+server.ts · tests/lib/workflows/run-helpers.test.ts (new, mutation-verified)

#9 — safe-eval RCE bypass closed done

The old regex denylist was bypassable with dynamic property access (this["cons"+"tructor"]["cons"+"tructor"]("…")() — a working escape that read process.env). Replaced with an AST allowlist: the expression is parsed (@babel/parser) and every node is walked, rejecting this, banned identifiers/property-names (constructor, __proto__, process, Function, eval, …), dynamic computed member access, and Function/eval calls. Function signature unchanged, so transform/conditional/validator/loop callers are untouched. A hand-rolled walk is used deliberately — visitor-table imports (acorn-walk) break under vitest's full-graph module loading.

src/lib/workflows/nodes/safe-eval.ts (rewrite) · tests/lib/workflows/nodes/safe-eval.test.ts (new — asserts the bypass is rejected and legitimate expressions pass)

#3 — dryRun guards done

code-execute (arbitrary JS/Py/bash in the sandbox) and http-request (real POST/PUT/DELETE) had no dry-run short-circuit, while ~13 other side-effecting nodes did. Both now return a simulated result on context.dryRun without executing — matching the email.ts/data-store.ts pattern.

src/lib/workflows/nodes/code-execute.ts · src/lib/workflows/nodes/http-request.ts · + dryRun tests

#12 — new control-flow primitives done

  • switch — deterministic n-way branch; evaluates an expression, sets metadata._selectedHandle to the matching case (or default) using the engine's existing n-way handle routing. (nodes/switch.ts + switch.def.ts)
  • loop concurrency — the previously-ignored concurrency config now drives a bounded pool; default 1 preserves the old sequential behaviour. (nodes/loop.ts, loop.def.ts)
  • approval — standalone human approve/reject node reusing the engine's existing pause/resume primitive, with no dependency on the scraper module. (nodes/approval.ts + approval.def.ts)

src/lib/workflows/nodes/{switch,approval}.{ts,def.ts} · loop.ts/.def.ts · index.ts · registry-client.ts · tests/lib/workflows/nodes/{switch,approval}.test.ts

#14 / #17 / #18 — engine correctness & types done

  • #14 self-healing now applies healed config to a per-run copy and no longer writes it back to workflow_nodes — it was silently rewriting the user's saved workflow.
  • #17 fan-in key collisions (two upstream sources, same key, differing values) now emit a warning instead of silent last-writer-wins; merge result unchanged.
  • #18 engine-injected fields (_currentNodeId, _registry, _onError) are now typed on ExecutionContext, removing inline casts.

src/lib/workflows/engine.ts · src/lib/workflows/types.ts

#2 / #7 — Hermes generation grounding done

#2 new workflow_describe_node(type) MCP tool returns a node's full configSchema (required, enums, defaults), port types and an example — so the agent reads schemas proactively instead of discovering mistakes at write-time. #7 six golden few-shot exemplars (scrape→summarise→email; cron→fetch→notify; gmail-trigger→LLM→reply/label; conditional branch; loop map; scrape-diff-notify) added to the orchestrator prompt, with every node type verified against the real registry.

3 · Pending — specified, not yet written

These were blocked when the execution environment stopped allowing sub-agent dispatch and reliable file edits. Each has a concrete implementation plan ready to execute.

#11 — Cancel actually stops a run pending

Add a module-level Map<runId, AbortController> in the engine; register at run start; check the signal between node levels and link it to the per-node timeout controllers; export engine.cancelRun(runId) and call it from the cancel route after the DB status flip. Today a cancelled run keeps executing and spending LLM/tool cost.

engine.ts · engine-runtime.ts · routes/api/workflows/[id]/runs/[runId]/cancel/+server.ts

#10 — Graceful drain on shutdown pending

Track in-flight run promises; add engine.drain(timeoutMs) that stops new runs and awaits outstanding ones to a bounded timeout; call it from gracefulShutdown before process.exit. Today a deploy/restart abandons in-flight work (the deploy script's drain marks DB state honest but does not preserve the running work).

engine.ts · src/hooks.server.ts

#20 — Incremental output persistence pending

Persist each node's output/status at completion (reusing the now-runId-scoped write) rather than only at run resolution — caps memory on large fan-outs and preserves partial results across a crash. Must keep resume working.

engine.ts · run-helpers.ts

#13 — Extract the execute() god-method pending

Mechanically extract the self-healing loop and single-node execution body into helpers / a new engine-node-runner.ts, with zero behaviour change. Pure readability/testability; lowest functional value, so sequenced last among the engine items.

engine.ts → engine-node-runner.ts (new)

#4 / #5 — Expose the rich generator to Hermes & make verify blocking pending

The largest lift: a separate run-execution process driven by a DB-backed run queue, with pg advisory-lock leader election for the cron/scheduled lanes. To keep production safe this should land additive and feature-flagged off by default. The existing drain + reaper + resume combo makes the current in-process model survivable in the interim.
