# Workflow Engine Design Spec

**Date:** 2026-04-12
**Status:** Approved
**Replaces:** JKAI autonomous build system

## Overview

A visual workflow automation platform for strange_rambling_svelte that replaces JKAI and becomes the foundational orchestration layer. Users build workflows via a node-based canvas (Svelte Flow) or natural language chat with an AI orchestrator (GLM-5.1 via z.ai). Workflows string together functions (API calls, code execution, LLM calls, data transforms) and pass data between nodes. Each node's input/output data is inspectable SSIS-style, with breakpoint support for debugging.

New integrations are generated by the AI orchestrator from API descriptions, tested in a sandbox, and registered as reusable node types for future workflows.

**Single user** — no multi-tenancy, permissions, or quotas.

## Architecture: Engine Core + Thin Canvas Adapter (Approach C)

Four layers:

1. **Workflow Engine** (`src/lib/workflows/engine/`) — defines workflow/node/edge types, node registry, execution runtime with breakpoints, data capture, and event streaming. Knows nothing about Svelte Flow.
2. **Canvas Adapter** (`src/lib/components/workflows/`) — bidirectional sync between the engine model and Svelte Flow's visual model. Custom Svelte node components render based on engine node types.
3. **AI Orchestrator** (`src/lib/workflows/orchestrator/`) — takes natural language, produces engine workflow definitions via GLM-5.1 (z.ai). Uses a debate pattern (plan, critique, revise) for quality.
4. **Scheduler** (`src/lib/workflows/scheduler/`) — cron + event triggers that invoke the engine directly (no canvas needed).

## Workflow Engine

### Core Interfaces

```typescript
interface NodeExecutor {
  type: string
  execute(
    input: Record<string, any>,
    config: Record<string, any>,
    context: ExecutionContext
  ): Promise<NodeResult>
  getInputSchema(config: Record<string, any>): JsonSchema
  getOutputSchema(config: Record<string, any>): JsonSchema
}

interface ExecutionContext {
  workspaceDir: string              // shared sandbox filesystem for this run
  sandbox: SandboxExecutor          // reuse JKAI sandbox
  emit(event: WorkflowEvent): void  // real-time updates via EventEmitter
  getNodeOutput(nodeId: string): Record<string, any> | undefined
  checkBreakpoint(): Promise<void>  // async pause point
  abortSignal: AbortSignal
}

interface NodeResult {
  output: Record<string, any>
  logs?: string[]
  metadata?: Record<string, any>  // timing, token usage, etc.
}
```

### Execution Flow

1. **Build graph** — parse nodes + edges into a DAG
2. **Topological sort** — determine execution order, identify parallelisable groups
3. **For each node:**
   - Check breakpoints — if set, pause and emit `paused_breakpoint` event
   - Gather input — collect `outputData` from all upstream nodes, merge by edge mapping
   - Execute — call the node's executor with merged input + config
   - Capture — store `inputData`, `outputData`, `logs` in `nodeExecutions`
   - Emit — stream `node_started`, `node_completed`, `node_failed` events
4. **Conditional branching** — Conditional nodes return which output handle to follow. Only the matching downstream branch executes.
5. **Loop nodes** — iterate over an array in the input, running the loop body subgraph once per item, collecting results into an array output.

### Event Streaming

EventEmitter per run, exposed via SSE endpoint. Events:
- `run_started`, `run_completed`, `run_failed`
- `node_started`, `node_completed`, `node_failed`, `node_paused`
- `breakpoint_hit` (includes node ID and current data snapshot)
- `log` (stdout/stderr from sandbox nodes)

### Breakpoints

Stored as a `Set<nodeId>` on the run. At a breakpointed node:
1. Status set to `paused_breakpoint`
2. `breakpoint_hit` event emitted with input data snapshot
3. Engine awaits a Promise that resolves on user "continue"
4. User can edit input data before resuming — modified data replaces the original

## Node Registry

### Registry Interface

```typescript
interface NodeDefinition {
  type: string
  label: string
  category: 'trigger' | 'core' | 'integration' | 'control' | 'custom'
  description: string
  executor: NodeExecutor
  configSchema: JsonSchema
  defaultConfig: Record<string, any>
  inputs: PortDefinition[]
  outputs: PortDefinition[]
}
```

Built-in nodes registered at startup. Integration nodes loaded from `integrations` table and registered dynamically.

### Built-in Node Types

**Triggers:**
- **Manual Trigger** — no-op start node
- **Cron Trigger** — starts workflow on cron schedule
- **Webhook Trigger** — exposes URL, POST starts workflow with request body
- **Event Trigger** — fires on platform events (e.g. "new Strava activity synced")

**Core:**
- **HTTP Request** — method, URL (template variables), headers, body, auth. Output: status + parsed response.
- **Code Execute** — JS/Python/Bash in sandbox. Input available as `input` variable. Script output becomes node output.
- **LLM Call** — model selection (OpenRouter), system/user prompts (templated), temperature, max tokens. Output: response text + usage metadata.
- **Transform** — JS expression/function to reshape data. Runs in-process (not sandboxed).
- **Data Store** — read/write key-value store scoped to the workflow, persisted in a dedicated DB table (not in-memory). Survives across runs for stateful workflows (e.g. "last processed activity ID").

**Control Flow:**
- **Conditional** — JS expression, routes to one of N output handles
- **Loop** — iterates array, runs all downstream nodes within the loop scope once per item, collects results into output array. Configurable concurrency.
- **Delay** — waits configurable duration
- **Error Handler** — wraps subgraph, catches failures, routes to error branch

**Integrations (pre-built, first-class):**
- **Strava** — all API operations (list activities, get activity, get athlete, get stats, get segments, get routes). OAuth via existing `oauthTokens` table. Wraps existing `src/lib/health/` functions.
- **Whoop** — all API operations (get cycles, recovery, sleep, workouts, body measurements). OAuth via existing tokens. Wraps existing health functions.
- **OpenRouter** — chat completion, model list, generation stats. Uses existing `openrouter` lib.
- **Email** — send via SMTP (Nodemailer). To, subject, body (templated), attachments.

Each integration node shows a dropdown of available operations. Selecting an operation updates input/output schemas and config panel.

## AI Orchestrator

### LLM: GLM-5.1 via z.ai

The orchestrator uses the existing `src/lib/zai/` integration, NOT OpenRouter. OpenRouter is only used as a workflow node for in-workflow AI steps.

### Chat Interface

Chat panel alongside the canvas. User describes intent, orchestrator generates a workflow.

### Planning Rounds (debate pattern)

**Round 1 — Planner:** Given user request + available node registry, produce workflow definition as structured JSON (nodes with types/configs, edges, explanation per step).

**Round 2 — Critic:** Reviews for missing error handling, data shape mismatches, unnecessary complexity, missing nodes.

**Round 3 — Revision:** Addresses feedback, outputs final workflow definition.

Canvas renders after Round 3. No execution until user approves.

### Integration Generation

When a requested integration doesn't exist:
1. Orchestrator recognises missing node type
2. Asks user for confirmation to create it
3. Generates integration definition (from AI knowledge or user-provided OpenAPI spec URL)
4. Tests a sample API call in the sandbox
5. Stores in `integrations` table, registers in node registry
6. Continues building the workflow

### Workflow Modification

Chat can modify existing workflows on canvas:
- "Add error handling to the Strava node"
- "Replace the email step with a Slack message"
- "Make this loop run in parallel"

Orchestrator reads current workflow state, applies modification, updates canvas.

### Prompts

System prompts live in `src/lib/workflows/orchestrator/prompts.ts`.

## Canvas UI

### Route Structure

- `/workflows` — workflow list (name, trigger type, last run status/time)
- `/workflows/[id]` — canvas editor
- `/workflows/new` — new workflow (empty canvas + chat)

### Layout (three panels)

**Left sidebar — Node palette:**
- Grouped by category (triggers, core, control flow, integrations)
- Drag nodes onto canvas
- Search/filter at top

**Centre — Svelte Flow canvas:**
- Nodes, edges, zoom, pan, minimap
- Toolbar: run/pause/stop, breakpoint toggle, save, undo/redo

**Right sidebar — Context-sensitive:**
- **Chat panel** (default) — orchestrator conversation
- **Node inspector** (on double-click) — config, schema, data tabs

### Custom Node Components

Each node type rendered as custom Svelte component in Svelte Flow:
- Node icon + label
- Port dots for inputs/outputs (colour-coded by data type)
- Status indicator during execution (spinner, check, X)
- Breakpoint indicator (red dot)

### Node Inspector (double-click) — Three tabs

**Config:** Form fields driven by `configSchema`. HTTP Request: method, URL, headers, body. LLM Call: model, prompts, temperature.

**Schema:** Read-only input/output JSON schemas. During a run, shows actual data alongside schema.

**Data:** Visible during/after run. Real `inputData` and `outputData` as expandable JSON tree. Truncated with "show full" toggle for large payloads.

### Edge Inspection

Click edge to see:
- Source output schema → target input schema
- During/after run: actual data that flowed
- Type mismatch indicator

### Run Visualisation

During execution:
- Nodes animate: grey (pending) → blue pulse (running) → green (completed) → red (failed) → yellow (paused)
- Edges animate with flowing dot/dash pattern
- Currently executing node highlighted
- At breakpoint: inspector auto-opens with editable JSON + "Continue" button

## Scheduling & Event Triggers

### Cron Scheduler

Server-side process (via `hooks.server.ts`):
- On startup, loads enabled `workflowSchedules` where `type = 'cron'`
- Uses `croner` (pure JS cron library) to register jobs
- Each tick: creates `workflowRun`, invokes engine, updates `lastRunAt`/`nextRunAt`
- Hot-reloads when schedules change (no server restart)

### Event Triggers

In-process event bus:
- **Strava activity synced** — emitted after health sync
- **Whoop recovery updated** — emitted after Whoop sync
- **Webhook received** — POST to `/api/workflows/webhook/[workflowId]`
- **Workflow completed** — one workflow finishing triggers another

### Schedule UI

Workflow canvas toolbar → trigger config button → modal:
- Manual (default)
- Cron — expression builder with presets + raw input
- Event — dropdown of event types + optional filter
- Webhook — shows generated URL

## Migration from Existing Features

### JKAI → Deprecated
JKAI code stays in codebase but routes/UI point to workflows. Capabilities absorbed:
- Code execution → Code Execute node (same sandbox)
- Debate planning → Orchestrator planning rounds
- Build serving → out of scope (workflows are data/automation pipelines)

### Deep Dive → Expressible as a Workflow (future)
Could be represented as: Trigger → LLM Call (queries) → Loop → HTTP Request (search) → LLM Call (extract) → Transform (merge) → LLM Call (synthesis) → Data Store. Not migrated in v1.

### CDO → Same (future)
Rebuild as workflow chaining Deep Dive into synthesis. Not v1.

### Agent System → Reused
Existing `agentTasks`, `agentActions`, `agentActivity` tables and SSE patterns kept. Workflow runs emit through the same activity system for unified feed.

### Health Integrations → Wrapped
Strava and Whoop nodes wrap existing `src/lib/health/` sync/fetch functions. OAuth via existing `oauthTokens` table.

- Node registry with 3 initial nodes: Manual Trigger, Code Execute, Transform
- Svelte Flow canvas with custom node rendering
- Canvas adapter (engine ↔ Svelte Flow sync)
- Save/load workflows to database

### Phase 2: AI Orchestrator + Chat
- GLM-5.1 integration for orchestrator
- Chat panel UI
- Planning rounds (plan, critique, revise)
- Workflow generation from natural language
- Workflow modification via chat

### Phase 3: Data Inspection + Breakpoints
- Node execution data capture (inputData/outputData)

- Edge data inspection
