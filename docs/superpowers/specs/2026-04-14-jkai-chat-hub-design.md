# JKAI Chat Hub — Design Spec

## Overview

Centralised chat interface at `/jkai` that serves as the primary interaction point with the orchestrator. Replaces the current builds list as the landing page, provides seamless WhatsApp conversation continuation, surfaces job metrics, and consolidates access to system prompts and chat history.

## Goals

- Single chat interface for all orchestrator capabilities (general chat, workflow generation/modification, tool use)
- Seamless continuation of WhatsApp conversations on the web
- Browseable conversation history with persistent threads
- Compact metrics about scheduled/running/completed/failed jobs
- Centralised access to system prompts editor and JKAI builds

## Data Model

### New `conversations` table

```
conversations
  id: text (UUID, PK, default gen_random_uuid)
  title: text (nullable — auto-generated by truncating first user message to ~50 chars)
  source: text ('web' | 'whatsapp-continuation')
  whatsappPhoneNumber: text (nullable — set when continuing a WhatsApp thread)
  createdAt: timestamp (default now)
  updatedAt: timestamp (default now)
```

### Extend `orchestratorChats` table

- Add `conversationId` column: `text`, nullable, FK to `conversations.id` with `onDelete: cascade`
- Existing rows with `workflowId` continue working unchanged (backwards compatible)
- New jkai chat messages use `conversationId` instead of `workflowId`

### WhatsApp data stays separate

- `whatsappConversations` table unchanged — bridge continues writing there
- WhatsApp continuation reads from `whatsappConversations` for display, web replies go to `orchestratorChats` with `conversationId`
- LLM receives merged history (WhatsApp + web) as context

### Chat history loading for WhatsApp-continued conversations

1. Load WhatsApp messages by phone number from `whatsappConversations` (read-only)
2. Load web messages by `conversationId` from `orchestratorChats`
3. Merge chronologically for display
4. Send combined history to `generalChat()` as conversation context

## Chat & Orchestrator Integration

### Mode routing

- Default is general chat (no mode) — same behaviour as WhatsApp
- Workflow generation/modification via explicit `mode` field when needed
- All existing tools available: health, blog, JKAI builds, research, Home Assistant

### API changes to `/api/workflows/orchestrator/chat`

POST body gains optional `conversationId` field:
- When `conversationId` set and no `workflowId`: loads history from that conversation
- Saves user + assistant messages with `conversationId`
- When both set (chatting about a specific workflow): saves with both

### New API routes

| Route | Method | Purpose |
|-------|--------|---------|
| `/api/jkai/conversations` | GET | List conversations (title, source, updatedAt, preview) |
| `/api/jkai/conversations` | POST | Create new conversation, returns `{ id }` |
| `/api/jkai/conversations/[id]` | GET | Get conversation with messages |
| `/api/jkai/conversations/[id]` | DELETE | Delete a conversation |
| `/api/jkai/metrics` | GET | Summary counts: scheduled, running, completed, failed |
| `/api/jkai/whatsapp-thread` | GET | Latest WhatsApp conversation history by configured phone number |

### WhatsApp continuation flow

1. User clicks "WhatsApp thread" in sidebar
2. Frontend calls `GET /api/jkai/whatsapp-thread` to load history
3. Creates new conversation via `POST /api/jkai/conversations` with `source: 'whatsapp-continuation'` and `whatsappPhoneNumber`
4. Displays WhatsApp messages with visual distinction (e.g. subtle WhatsApp icon on bubbles)
5. User types — goes through normal orchestrator chat flow with combined history as context

## Route Structure

### New routes

```
/jkai                    → chat page (new)
/jkai/builds             → builds list (moved from /jkai)
/jkai/builds/[id]        → build detail (moved from /jkai/[id])
/jkai/builds/new         → new build (moved from /jkai/new)
/jkai/prompts            → system prompt editor (moved from /workflows/prompts)
```

### Migration

- Current `/jkai` page (builds list) moves to `/jkai/builds`
- Current `/jkai/[id]` moves to `/jkai/builds/[id]`
- Current `/jkai/new` moves to `/jkai/builds/new`
- `/workflows/prompts` route removed — page moves to `/jkai/prompts`
- Prompts API routes (`/api/workflows/prompts`) stay in place — only UI page moves
- ChatPanel in workflow editor stays as-is for now (workflow-specific context)

## Component Architecture

### New components

- `src/lib/components/jkai/ChatHub.svelte` — main chat page layout (sidebar + chat + header)
- `src/lib/components/jkai/ConversationSidebar.svelte` — conversation list with WhatsApp indicator
- `src/lib/components/jkai/MetricsStrip.svelte` — compact metrics bar
- `src/lib/components/jkai/ChatArea.svelte` — refactored from ChatPanel, full-width, conversation-aware

### Reused components

- `ChatMessage.svelte` — individual message bubble (unchanged)
- `ThinkingTimeline.svelte` — thinking step visualisation (unchanged)

## Styling

Follows existing site design system:
- CSS custom properties: `--bg`, `--card-bg`, `--card-border`, `--accent`, `--text-primary`, `--text-secondary`, `--text-ghost`
- Font families: `--font-body`, `--font-mono`
- Full-height layout (min-height: 100vh minus header)
- Consistent with existing jkai layout root styling

## Out of Scope

- Replacing the workflow editor's embedded ChatPanel (future consideration)
- Real-time WebSocket/SSE streaming (stays with polling for now)
- Multi-user auth (single-user system)
- Mobile-optimised layout (functional but not a primary target)
