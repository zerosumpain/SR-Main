## Solver API (`$lib/trips/solver`)

All functions are deterministic: same input, same output (no `Date.now()`,
no `Math.random()`; ties break on ids).

```ts
interface SolverInput {
  trip: Pick<Trip, 'id' | 'timeZone' | 'startDate' | 'endDate' | 'pace' | 'modes'>;
  stays: Stay[];
  wishes: Wish[];          // suggested/skipped wishes are ignored
  bookings: Booking[];     // status 'booked' with date+startMin = hard window
  matrix: TravelMatrix;    // points = wish ids + `stay:<id>`
}
solveTrip(input: SolverInput): SolvedPlan

interface ReplanInput {
  trip, stays, wishes, bookings, matrix;   // as above
  day: PlannedDay;                         // the day as currently planned
  nowMin: number;                          // local minutes now
  position: LatLng | null;                 // where the phone is
  atStopId: string | null;                 // stop the phone is at, if any
  doneStopIds: string[];                   // visited or skipped already
}
replanDay(input: ReplanInput): ReplanOption[]   // at most 3, best first
retimeDay(day: PlannedDay, fromIndex: number, startMin: number,
          input: Omit<ReplanInput, 'day'|'nowMin'|'position'|'atStopId'|'doneStopIds'>): PlannedDay
```

Rules: musts before nices; locked/booked items never move off their day/time;
stays start and end each day (`stay:<date>:start|end` stops); lunch (and
dinner for `packed`) are `meal` stops placed in their window at the cheapest
point; leg mode = walk if walk time ≤ `walkLimitSec` else the fastest allowed
mode with a route; a nice that no longer fits is dropped with a reason; a must
that cannot fit stays with a warning. Default visit length when unknown: 60 min.

The phone (SR-AppleApp) ports `retimeDay` and `replanDay` to Swift with the
same test cases (`solver/fixtures/*.json` are the shared cases — export them).

## Phone wire contract (`/api/native/trips`)

JSON, camelCase. Times on the wire: local minutes for plan times (with the
trip's `timeZone`), ISO 8601 for instants. Coordinates are `{lat,lng}`.
Every handler is `withNativeAccess` and owner-only (403 for members, D2).

- `GET /api/native/trips` → `{ trips: TripSummary[] }`
  `TripSummary = { id, title, destination, timeZone, startDate, endDate, status, planVersion: number|null, updatedAt }`
- `GET /api/native/trips/:id` → `TripBundle`
  ```
  TripBundle = {
    trip: Trip,
    stays: Stay[],
    wishes: Wish[],
    bookings: Booking[],
    plan: { id, version, createdAt, plan: SolvedPlan, changes: string[] } | null,
    matrices: { [date: LocalDate]: TravelMatrix },  // per day: that day's stops + its stay only
    etag: string
  }
  ```
  Supports `If-None-Match` → 304.
- `POST /api/native/trips/:id/events` body `{ events: TripEvent[], basePlanVersion: number }`
  → `{ accepted: string[] /* clientIds */, planVersion: number }`. Idempotent on
  `clientId`. `option-applied` with `detail.day` (a `PlannedDay`) stores a new
  plan version with `source: 'phone'` replacing that day only.
- `POST /api/native/trips/:id/replan` body `{ date, nowMin, position, atStopId, doneStopIds }`
  → `{ options: ReplanOption[] }` (server-side full options, may use other days later).

Conflict rule: while a day is running, the phone's version wins for that day.
A site edit to today that arrives after a phone version is listed under
`changes` as "Changed on the site while you were out — " so the phone can show it.

## D1 storage check (2026-10-13)

Read: Mapbox Product Terms, version of 21 July 2026 (the PDF linked from
mapbox.com/legal/product-terms).

- §2.10.1 *Navigation APIs*: "Customer shall not export, download, cache or
  store results from any request to a Navigation API." Directions and Matrix
  are Navigation APIs.
- §1.9 (default restrictions, unless an Order says otherwise): query only "in
  response to human user queries", no "bulk or automated queries", and do not
  "cache or store … results from the Service Offerings".
- §2.7.2: Temporary Geocodes (our Search Box tier) may not be stored either —
  already the rule in `$lib/maps/mapbox-api`.

So storing is NOT allowed. What the build does:

- Stored plan figures and the stored `trip_plan.matrix` (which the phone
  receives per day and re-times from offline) come from openrouteservice
  (walk/cycle/drive matrix and directions) and Transitous (transit), cached per
  pair in `app_settings` for 30 days, and otherwise from the solver's
  distance × factor estimate, marked `estimated`. Never from Mapbox.
- Mapbox Directions + Matrix are restored (`$lib/maps/mapbox-api`,
  `MAPBOX_NAVIGATION_IS_LIVE_ONLY`) for live-only use: `GET
  /api/trips/:id/live?date=` returns that day's drive legs with live traffic
  for display, `no-store`, written nowhere. The server-side `/replan` uses the
  stored matrix, so an applied phone option never carries a Mapbox figure.
- Places come from OpenStreetMap (Nominatim / Overpass), never Mapbox Search.
- Transitous (api.transitous.org) is for non-commercial, light use with a
  User-Agent and attribution to transitous.org/sources; requests are
  serialised, capped per background fill, and never block an edit.

## v2 (owner, 2026-10-14) — conversation-led planning, a read-only phone plan, off-plan re-planning

Owner's words, condensed: the phone's normal view shows **just the plan** — no
input boxes (an "Edit plan" button changes it) — with **time left at the
current place** and **the next stage including directions and useful
information**: walking → a route; taxi → how to book, with links; transit →
which line, where. **All the information in the input forms is derived from a
model call**: the plan is developed through an **ongoing conversation with a
model**, refined and redeveloped interactively. When someone **goes off the
plan**, the app **offers suggestions and re-plans the rest of the trip** from
where they are and what they're doing.

New shared types are in `model.ts` under "v2" (`taxi` mode, `LegGuidance`,
`StopGuide`, `TripGuide`, `TripMessage`, `TripOp`, `ConverseResult`,
`Observation`, `TripReplanOption`).

### The conversation is the editor (site and phone)

- New table `trip_message` (grant it): id, trip_id, role, text, ops jsonb,
  plan_version, surface, created_at. `trip.guide` jsonb holds the `TripGuide`.
- `POST /api/trips/:id/converse` (site, owner session) and
  `POST /api/native/trips/:id/converse` (phone) take `{ text }` and return
  `ConverseResult`. New trip: `POST /api/trips` with `{ text }` creates the
  trip from the opening message ("Rome, 27–30 Oct, staying near Campo de'
  Fiori, want the Vatican and good food").
- One turn = one call through `$lib/llm/client` (planner workload, a capable
  model — this is the product's brain; not the cheap extraction workload)
  with: the trip, stays, wishes (with facts summary), bookings, the current
  plan summary (per day: stops/times/warnings/dropped), the last ~30
  messages, today's date/time in the trip zone, and — on the phone — the
  phone's position/observation if sent. It must return JSON
  `{ reply, ops: TripOp[], quickReplies }`. The server validates and applies
  ops IN ORDER (place queries resolved via OSM; research queued as before),
  re-solves once, stores both messages, returns `ConverseResult`. Invalid ops
  are rejected with a reason and the reply is still shown.
- The model drives intake: it asks for what's missing (dates, stays, pace,
  who's travelling, how they like to get about), proposes wishes and
  suggestions, explains warnings ("The Borghese needs booking 3 weeks ahead —
  want me to add it to the checklist?"), and re-develops the plan on request
  ("make Thursday lighter", "swap the Vatican to the morning").
- The site page becomes conversation-first: the conversation beside the
  plan (map + timeline). The forms stay as a **derived view** of the
  constraints, filled by the conversation; a direct form edit still works and
  is logged as an `event` message with its ops so the model sees it.
- Bundle (`GET /api/native/trips/:id`) gains `messages: TripMessage[]` (last
  50) and `guide: TripGuide | null`.

### Guidance (model-written, stored)

- After each solve, generate `LegGuidance` for every leg of today and the
  next day lacking it (others lazily, or on page view), cached by
  (from, to, mode, date) so re-solves reuse it. Inputs: routed data (ORS
  walking instructions → `steps`; Transitous itinerary → `transit` lines,
  stops, departures), the `TripGuide`, and the stop names. Taxi legs get
  `booking` from `TripGuide.taxi` (official ranks, the city's taxi number,
  apps that operate there — real links only, never invented URLs; when
  unsure say so in `how` and give no link). `StopGuide` per planned wish from
  its facts + one model call (entry rules, tickets, dress code, best
  entrance, what not to miss). `TripGuide` once per trip from one web search
  ("getting around <city>: taxis, public transport tickets") + one model call.
- Mapbox storage rule (D1) still holds: guidance text must not contain
  Mapbox-derived durations; use ORS/Transitous/estimate figures.
- Taxi as a mode: `taxi` time = drive matrix + `TAXI_PICKUP_SEC`; it is
  allowed when `trip.modes` includes it. Leg choice: walk if ≤ walk limit,
  else fastest allowed (taxi competes with transit).

### Off the plan (phone detects, server re-plans the trip)

- Phone detection (foreground + significant-change/region wake-ups; no
  continuous GPS except while following a walk):
  - `behind`: past a stop's planned depart by > 10 min, or ETA to next stop
    makes a locked slot late.
  - `off-route`: on a leg, moving and distance to the next stop increasing
    for > 5 min and > 300 m off the leg line.
  - `unplanned-stop`: stationary > 12 min more than 150 m from every planned
    stop (reverse-geocode the place name on the phone).
  - `out-of-order`: arrived at a later stop of today.
  - `idle`: at a stop > 20 min past its planned depart.
  One prompt per condition (no nagging); dismissible ("I'm fine").
- `POST /api/native/trips/:id/replan` body gains optional
  `scope: 'day' | 'trip'` (default `day`) and `observation: Observation`.
  Response gains `tripOptions: TripReplanOption[]` (scope `trip`) and
  `narrative: string` (one model call: what's happening and what it'd do,
  including a fresh suggestion near them if fitting — offered as a quick
  reply that posts to `/converse`).
- Solver gains `replanTrip(input: ReplanInput & { observation: Observation | null }): TripReplanOption[]`
  (≤3, deterministic): `carry-on` (today via replanDay's best, later days
  unchanged), `resolve-rest` (re-solve today-from-now + all later days with
  done/skipped removed; unfinished musts move to later days; locked/booked
  never move), `pull-forward` (bring later-day wishes near the current
  position into today now, re-solve the days they left), `stay-here`
  (unplanned-stop: extend the current dwell, push/drop the rest).
- Applying a trip option: event `option-applied` with `detail.days`
  (PlannedDay[]) — the server stores a phone version replacing those days.
- Bundle gains `tripMatrix: TravelMatrix` (all points) so the phone can do a
  simple offline pull-forward; full `replanTrip` is server-only.

### Phone views

- **Default (read-only) Day view:** "At the Pantheon — 25 min left" with
  leave-by and a countdown → **Next stage card** by mode: walk = small map
  with the route + "Start walking directions" (existing follower) + steps;
  transit = line/vehicle/from-stop/to-stop/stops/next departures + ticket
  tip + "Open in Maps"; taxi = how to get one + buttons (call, app links) +
  cost; drive = Maps hand-off. Then `StopGuide` tips for the next stop. Then
  the rest of today as a quiet read-only list. No inputs on this view.
- **Edit plan:** opens the conversation (same `/converse`, surface `phone`),
  with the keyboard's dictation; replies and changes appear inline; the plan
  refreshes from the result. Skip/late quick actions live in this sheet's
  quick replies, not on the plan.
- **Off-plan prompt:** a card at the top of the Day view: what was noticed,
  the narrative, up to 3 options (trip options when online, day options
  offline), one tap applies.

## v3 (owner, 2026-10-14) — a planner that already knows you and researches on its own

Owner's words, condensed: the model should already know his preferences from
his other engagements — JKAI memory and what's known about his family — and
should feel empowered to research a little on its own. Example: "my flight
leaves Newcastle at 07:35" → find the flight, work out when it lands, and
reason whether the gap between landing and hotel check-in is big enough to do
something, or whether it's lunchtime and they should grab food.

**D4 is relaxed:** the planner may run a few lookups per turn on its own
(budget below), not just one search per wish.

### What it already knows (TravellerProfile)
- On trip creation, and on demand ("what do you know about us?"), gather a
  `TravellerProfile`: `retrieveMemories` / `jkai_memories` (preferences,
  people, health, places, patterns), `searchKnowledge` for travel/food/
  holiday history, and the family roster for who's travelling. Owner-only
  (D2): a member's private data never enters this. Store on the trip
  (`trip.profile` jsonb); show it on the site as "What I know about you",
  with sources, editable via the conversation (`updateProfile`).
- Every planner turn's prompt includes the profile. The model uses it
  without being told ("you prefer walking, so…") and says when it did.
- `remember`: when the owner states a lasting preference ("we never do early
  starts"), the model may save it to JKAI memory via the existing
  `writeMemory` path (category, assertion 'stated', source = the trip
  message), and says so in the reply.

### Getting there and back (TransportSegment)
- New table `trip_transport` (grant it). Ops `addTransport` /
  `updateTransport` / `removeTransport`.
- Solver: the arrival day starts at `arrive` (+ delay) + `exitMin` +
  transfer (airport → stay, or → the first stop if bags can be left), and
  a "Drop bags" stop at the stay comes first if arriving before check-in;
  the departure day ends at `depart` − `checkInLeadMin` − transfer, after
  check-out. Stays' `checkInMin`/`checkOutMin` are now used. Transfer legs
  use the matrix with the airport/station as a point (`transport:<id>:from|to`).
- Phone: the transport segment shows as the first/last stage card (flight
  number, times, terminal if known, status); on travel days the app may
  poll status when a live flight-status source is configured.

### Research on its own (agentic turn)
- A planner turn runs through `$lib/llm/tool-loop.ts` with a small toolset
  and a budget: at most 6 tool calls and 4 web searches per turn, every
  search in the Tavily ledger; a turn's research is returned as
  `ConverseResult.research` and shown under the reply with sources.
- Tools: `web_search` (Tavily), `read_page` (fetch + extract one URL),
  `find_place` (OSM), `opening_hours`, `travel_time` (matrix/ORS/Transitous/
  estimate), `flight_lookup` (number and/or route + date → scheduled
  depart/arrive, airports, terminal; from a flight-status API when a key is
  registered in the secret registry — dormant otherwise — else web search +
  extraction, marked `researched`), `recall` (JKAI memory/knowledge search).
- The prompt tells it to look things up when a fact matters to the plan
  (arrival times, opening hours on the day, whether a place takes
  bookings), to reason about gaps (landing → transfer → check-in → lunch),
  and to propose what fits — not to research for its own sake.

## v4 (owner, 2026-10-14) — the trip designer studio

Owner's words: "a 'trip designer studio' look and feel, with a tab per day,
and each day broken down into a few stages: breakfast and morning plans,
lunch, afternoon plans, dinner and evening. I want them to be visually
different. The UI needs an overhaul to include that capability."

- **Stages** (`DayStage`, `DAY_STAGE_LABEL` in model.ts): every planned stop
  carries `stage`, set by the solver: morning = day start → lunch;
  lunch = the lunch meal (or the wish that replaces it); afternoon = after
  lunch → dinner (or 18:00); evening = dinner and after.
- **Meals for every pace:** breakfast (at the stay by default, ~30 min at
  day start; a wish may `replacesMeal: 'breakfast'` — a café) and dinner
  (all paces; window 19:00–21:30, relaxed 19:30–21:30) are planned meals,
  so every stage has substance. The "back at the stay by" time moves to
  after dinner; light/normal/full capacity still counts active (non-meal)
  time, so days don't get busier.
- **Site — the studio** (`/trips/[id]` overhaul): a studio layout with a
  **tab per day** (plus an Overview tab: all days on the map, bookings
  checklist, what I know about you, transport). A day tab shows the day's
  map and the four stages as visually distinct bands (each stage its own
  tint/texture/heading treatment from the site's design tokens — not the
  reserved categorical hues), each listing its stops with times, legs and
  guidance, and an "Ask about this stage" affordance that pre-fills the
  conversation ("Something different for Wednesday lunch?"). The
  conversation stays docked beside the studio; a reply that changes the
  plan updates the open tab and briefly highlights what changed. Forms stay
  as a "Details" drawer.
- **Phone:** the read-only Day view groups the rest of today by the same
  four stages with matching treatment; the trip screen's days list shows
  each day's four stages in brief.

Bundle gains `suggestions: TripSuggestion[]` (pending + last 20 decided).

### Phone bundle additions
- `access: TripAccess`, `suggestions`, `fullness: Record<LocalDate, DayFullness>` (computed server-side from the plan + pace rules + day loads: active minutes vs capacity; bands empty <10%, light <50%, balanced <85%, full ≤100%, overfull >100%).
- Every leg gains `alternatives: LegAlternative[]` (walk, taxi, transit when allowed/known — from the trip matrix via the solver's `modeSeconds`; taxi = drive + pickup).
- `GET /api/native/trips/:id/route?from=<stopId>&to=<stopId>&mode=<mode>&date=<date>` → `{ line: LatLng[], durationSec, distanceM, estimated, guidance: LegGuidance | null }` for any mode (ORS/Transitous/estimate; never stored Mapbox figures), cached like legs.

### Phone

- Day screen: each stage/gap has "Make a suggestion" → calls `/ideas` and shows up to 3 cards inline; creator/parent: "Add this"; member: "Suggest this" (creates a suggestion). Pending suggestions show in their slot; parents get Approve / Reject inline.
- Every stop shows the leg from the previous stop (first: from the stay) with a small route map and a mode picker (Walk · Taxi · Metro/transit, with each one's approximate minutes); picking one re-draws that route via `/route` (display only — it does not change the plan).

## v6 (owner, 2026-10-14) — "Make a suggestion" must work every time

Owner: "The make a suggestion doesn't always work — in fact more often than not doesn't work."

Diagnosis (production, 2026-10-14):
- The app's `SiteClient` gives every request a 30 s timeout and no trips call overrides it. `/ideas` (agentic turn + OSM + solver checks) takes ~40–90 s, so most asks time out on the phone. The same hits `/converse`, trip creation and trip-scope `/replan`. Cloudflare also cuts a proxied request at ~100 s, so a longer client timeout alone is not a fix.
- When the planner errors, `/ideas` returns early without logging, so failures were invisible.
- One logged ask (a 77-min lunch gap) returned zero drafts ("Nothing fitted" with nothing turned down): the model answered with no usable ideas and there was no fallback.

### Async model-backed calls (server + app)
- `POST /api/native/trips/:id/ideas`, `POST /api/native/trips/:id/converse`, `POST /api/native/trips` (create) and `POST /api/native/trips/:id/replan` with `scope:'trip'` accept `"async": true` in the body. With it they answer at once `202 { job: { id, kind, status: 'running', startedAt } }` and do the work in the background. WITHOUT it they behave exactly as today (build 0.1.104 on phones keeps working).
- `GET /api/native/trips/jobs/:jobId` → `200 { job: { id, kind: 'ideas'|'converse'|'create'|'replan', status: 'running'|'done'|'failed', startedAt, finishedAt|null, result: <the same JSON the synchronous call returns>|null, error: string|null } }`. Only the caller who started it may read it (else 404). Jobs live in memory for 30 min after finishing; an unknown id (e.g. after a deploy restart) is 404 → the app says "That got lost in an update — try again".
- A job that runs longer than 150 s is failed with a plain message.
- The site page uses the same jobs for ideas and the conversation (session routes `GET /api/trips/jobs/:jobId`).

### Ideas that always come back
- Smaller budget for the ideas turn (≤4 tool calls, ≤2 web searches) and one JSON repair retry when the answer is unreadable.
- **Deterministic fallback**: when the model fails, times out, or returns no idea that fits, query OpenStreetMap (Overpass) around the gap — restaurants/cafés for a meal slot (respect dietary hints only as a soft ranking), otherwise attractions, museums, viewpoints, parks, churches, markets — within a walk/transit radius that the gap allows, rank by closeness to the line between the stop before and after, verify each with the solver, and return up to 3 that fit (source 'nearby' vs 'planner' on each idea).
- Verification: a meal-slot idea that replaces the meal counts as landing in that stage; an idea that lands in the adjacent stage but entirely inside the gap's times also fits.
- Every outcome is logged as an event (found / nothing fitted with each turned-down reason / planner error with the error kind) so failures are visible.
- Response gains `source` per idea and keeps `rejected` + `note`; the app shows the reasons when nothing fits, and a "Try again" button.

## v7 — Real meals and place photographs (2026-10-15)

From the red team (Drive `Architecture/2026-10-15-trip-planner-app-red-team.md`, proposal B): meals were times with no place, and no place had a picture.

### Meal options (`meals.ts`, `meals.server.ts`)
- Every planned lunch and dinner stop with no place gains `mealOptions` in the BUNDLE (never stored on a plan version, never solved on): up to three real places from OpenStreetMap near the placed stop before it (or after), within a 15-minute walk, open for the meal by their own `opening_hours` (a place may open up to 30 min into the meal; one known to be shut is never offered; one with no hours on record is offered and SAYS so), different cuisines where it can, a soft nudge for the profile's dietary hints.
- `MealOption { id (OSM id), name, kind 'restaurant'|'cafe', cuisine|null, place {name, location, osmId, address}, walkMin, walkFrom, openText|null, openKnown, website|null, phone|null, diet[], outdoorSeating, wheelchair|null, wikidata|null, why, source: 'OpenStreetMap' }`.
- Found in the background after every solve and phone version (Overpass, then Nominatim's bounded search when Overpass is busy), cached in `app_settings` `trips.meals.<tripId>` by meal stop with a fingerprint of the place and half-hour it was asked about; a bundle read that finds a meal not yet looked up starts a run, and the next refresh carries it. Re-asked after 14 days.
- Choosing one is the existing path: a wish `{ place, replacesMeal, fixedDate }` (a parent adds it via suggest + approve; others suggest it). Days sent back by the phone have `mealOptions` stripped before storing.

### Photographs (`images.ts`, `images.server.ts`)
- `TripBundle.images?: Record<wishId | mealOptionOsmId, PlaceImage>`; `PlaceImage { url (~800 px on upload.wikimedia.org), width, height, credit|null, license|null, sourceUrl (Commons file page), wikidata }`. The credit and licence must be shown with the photo.
- Only the place's own Wikidata image claim (P18), reached from its OSM `wikidata` tag (one paced Nominatim lookup per place, cached per trip in `trips.images.<tripId>`); never an image search. Images cached across trips in `trips.images.wikidata` (a miss re-checked after 30 days). No new table, so no runtime GRANT.
- Deleting a trip deletes its `trips.meals.*` and `trips.images.*` rows.
