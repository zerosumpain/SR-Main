# Curate — A New Orchestrator Experience For Building Workflow Nodes

**Status:** Design (2026-05-07)
**Scope:** New orchestrator mode that designs and ships first-class workflow nodes from a goal statement. First worked example: an Apple Calendar (CalDAV) node.
**Owner:** John

---

## 1. Goals & Non-Goals

### Goals

- Add a new orchestrator experience, **`curate`**, peer to the existing chat hub and autonomous builder, dedicated to creating brand-new workflow node types end-to-end.
- Curate must **discover** the right outcome — research libraries, APIs, auth patterns, existing in-repo conventions — *before* settling on an implementation. Specifically: avoid the existing orchestrator behaviour of reaching for `http-request` as a fallback when no node fits.
- The output is a **first-class repo node**: definition, executor, **node-specific Svelte config panel**, panel registry entry, sr-docs documentation, in-app help drawer. Indistinguishable in quality from hand-written nodes such as `gmail-send`.
- Pre-promotion (live-test) and post-promotion (deployed) must be **WYSIWYG**: the panel and executor you see during testing are the same artifacts that get merged and deployed.
- Promotion is the expected, frictionless ending of a curate session — a single click that merges the curate branch and runs the existing deploy pipeline.
- New integrations (Apple Calendar, Trello, Notion, Linear, Spotify, …) drop into a **generic credentials store**, not bespoke per-service tables.

### Non-Goals (v1)

- Editing or re-curating an existing node. v1 only creates new node types.
- Multi-user concurrency. Single-user assumption everywhere.
- Curating non-node artifacts (skills, prompts, sub-agents). Scope is workflow nodes only.
- Self-healing / autonomous retries on failed live-tests beyond a small bounded loop.
- Curate UI accessible from the production VPS instance. Curate runs on homeserv only (worktrees + per-session dev servers live there).

## 2. Architecture Overview

```
        ┌─────────────────────────────┐
        │   /jkai/curate (homeserv)   │
        │  Curate session UI          │
        └────────────┬────────────────┘
                     │
            ┌────────┴────────┐
            │  Curate Engine  │
            │  (in-process,   │
            │   homeserv)     │
            └────────┬────────┘
                     │
   ┌─────────────────┼─────────────────┐
   │                 │                 │
   ▼                 ▼                 ▼
Discovery       Generation        Promotion
toolkit         (worktree         (merge +
(web, ctx7,      writes repo       deploy.sh)
read-nodes,      files into
sr-docs,         curate branch)
opt sandbox)
                     │
                     ▼
            ┌─────────────────┐
            │ Per-session     │
            │ SvelteKit dev   │
            │ server          │
            │ homeserv:5180+  │
            └────────┬────────┘
                     │
                     ▼
              Live-test (real
              Svelte panel +
              real executor)
```

Curate runs in-process inside the homeserv SvelteKit instance. Every session opens a dedicated git worktree off `main`, writes the full repo set for the new node into that worktree, and runs an isolated dev server on a curate-allocated port. Live-test, iteration, and any panel UX work all happen against that dev server. Promotion merges the worktree's branch into `main`, pushes, and runs the existing `scripts/deploy.sh` to ship to the VPS.

The dynamic-node loader (`src/lib/workflows/orchestrator/dynamic-nodes.ts`) is **not** used by curate. It remains for any other dynamic-loading use case but plays no role in this design.

**Orchestrator awareness of new nodes.** The existing chat hub orchestrator surfaces available nodes to its LLM via registry-derived grounding (a JSON block built at runtime from `NodeRegistry`). Because every promoted curated node calls `registry.register(...)` in `src/lib/workflows/index.ts`, it shows up in grounding automatically — no edits to system prompts are required. Hand-curated prompt fragments that name specific nodes (e.g. the `general-chat.ts` paragraph about `stealth-scrape`) are not generated by curate; if a node ever earns one, it's authored by hand in a follow-up PR.

**LLM calls.** Curate's discovery, generation, and codegen phases all make LLM calls through the project's existing LLM gateway (the same surface used by the autonomous builder). No direct provider SDK calls.

## 3. Session Lifecycle

A curate session moves through six phases. Phases marked **[gate]** stop and wait for explicit user action; the rest are autonomous and stream their progress live into the chat.

### Phase 1 — Scope (chat)

Short conversational turn. Curate asks 1-3 targeted questions to nail the outcome — operations needed, scope of writes, services to support. Ends as soon as the orchestrator can write a one-line goal it's confident in.

### Phase 2 — Discovery (autonomous, streaming)

Curate runs an autonomous research pass with these tools:

- **Web search** (existing `WebSearch`/`WebFetch`)
- **context7** (already-wired MCP server) — fetches current library/SDK docs
- **Read existing repo nodes** — curate reads `src/lib/workflows/nodes/*.def.ts`, executors, and `src/lib/canvas/nodes/panels/*.svelte` to identify reusable auth/error/credential patterns and to set the design quality bar
- **sr-docs corpus** — `~/sr-docs/content/internal/features/workflows/nodes-*.md` for context on existing node design
- **Optional: sandbox API probe** — gated, opt-in. Uses the existing `jkai-sandbox` to run short read-only `fetch` snippets against the target API with a credential to confirm response shapes. Mutating probes require explicit per-call approval.

Discovery streams its narration into the chat as it works. The user can interject at any moment to redirect or correct.

### Phase 3 — Proposal **[gate]**

Discovery emits a single structured proposal card containing:

- Chosen integration approach (with reasoning, including rejected alternatives)
- Library / dependency choice. Bias is to **already-installed packages from `package.json`**; if a new dep is needed, the proposal calls it out explicitly (name, version, bundle size, license, maintenance status) and the user can choose to accept, swap for an alternative, or fall back to a "build it from stdlib + `fetch`" path. Either way, deps are added to `package.json` in the worktree — no vendoring, no separate dependency format.
- Auth pattern + credential schema (`apikey`, `basic`, or `oauth2`)
- Canonical node spec (see §4) — type, label, category, full `uiSchema`, executor design notes, output schema, deps
- Live wireframe of the proposed panel rendered inline in the proposal card
- 1-2 example test cases the live-test will run
- List of in-repo nodes the design borrowed patterns from
- Any deps that need installing

User chooses **Approve**, **Redirect** (free-form text correction → curate iterates back into Discovery), or **Reject** (ends session).

### Phase 4 — Generate (autonomous)

1. Verify `main` has a clean working tree. If dirty, stop and ask user to stash/commit/abort.
2. `git worktree add ~/.curate-sessions/<sessionId> -b curate/<type>-<sessionId>` from current `main`.
3. Write the full repo set into the worktree:
   - `src/lib/workflows/nodes/<type>.def.ts`
   - `src/lib/workflows/nodes/<type>.ts` (executor)
   - `src/lib/canvas/nodes/panels/<Type>Panel.svelte` (real, hand-editable Svelte)
   - Entry in `src/lib/canvas/nodes/panels/registry.ts`
   - Registration line in `src/lib/workflows/index.ts`
   - `~/sr-docs/content/internal/features/workflows/nodes/<type>.md` (written into the sr-docs repo via a per-session sr-docs branch — symmetric pattern)
   - `package.json` + `package-lock.json` updates if new deps were chosen
4. `npm install` if new deps were added (no-op if main already had them).
5. `npx tsc --noEmit` + lint as a safety check. On failure: stop, surface error, leave the worktree intact for inspection.
6. Allocate a port from the curate pool (`5180`-`5199`) and start a SvelteKit dev server inside the worktree.
7. Prompt the user inline for credentials. Saved encrypted to `integrationCredentials` (shared DB — visible to both the dev server and prod after promotion).
8. Surface a deep-link to the running dev server (e.g. `http://homeserv:5180/jkai/canvas?focusNode=<type>`).

### Phase 5 — Live test **[gate]**

Curate runs each test case from the proposal against the per-session dev server. Renders raw outputs in the chat. The user can:

- Open the dev server's canvas in a browser and *use the panel directly* — the real Svelte one, not a schema-rendered stand-in
- Confirm "looks right" → moves to Promote
- Push back ("date format is wrong", "panel needs a help section here") → curate iterates, edits the worktree, dev server hot-reloads via Vite HMR, re-runs the tests

The live-test loop is bounded — curate auto-stops asking after **5** consecutive failed-or-redirected iterations and asks the user whether to abandon the session, switch the underlying approach, or keep iterating manually.

### Phase 6 — Promote **[gate, but expected default]**

Single button. Promotion runs through:

1. Final `tsc --noEmit` + lint pass on the worktree
2. Squash-commit any iteration commits into one: `feat(workflow): add <type> node (curated)` with a body listing files, deps, and the source curate session id
3. `git checkout main && git merge --ff-only curate/<type>-<sessionId>` (rebase if main has moved)
4. `git push origin main`
5. Symmetric merge of the sr-docs branch into sr-docs `main` and push
6. `scripts/deploy.sh` (strange_rambling_svelte) and the sr-docs deploy script — both kicked off, logs tailed into the curate UI
7. **Verify live**: GET `/api/health/workflow-engine` on the VPS and confirm the new `type` is in the registry response; re-run the test cases against prod
8. Cleanup: stop the per-session dev server, free the port, `git worktree remove`, delete the curate branches (both repos)
9. Mark the session `status='promoted'` in `curateSessions`

Failure handling: any step's failure pauses the pipeline at that step. The UI shows the error and offers **Retry**, **Roll back** (`git reset --hard origin/main` and re-deploy if anything reached prod), or **Leave as-is for manual fix**.

Drain-on-deploy is a known existing concern (`project_workflow_engine_runtime`). Curate's promote step warns "deploying will kill `N` in-flight runs" if any are active and lets the user decide.

## 4. Components

### 4.1 Canonical Node Spec

A single TypeScript object representing everything about the node to be created. Persisted on the `curateSessions` row. Both definition + executor codegen and panel codegen render from it.

Fields:

- `type`, `label`, `category`, `description`
- `llmDescription`, `llmExamples` — for orchestrator grounding
- `inputSchema`, `outputSchema` (JSON Schema)
- `configSchema`, `defaultConfig`
- `uiSchema` — declarative description of the config panel (see §4.2)
- `summarize` — short JS source string rendering a one-line canvas preview
- `executor` — TypeScript source for the executor
- `deps` — list of `{ name, version }` packages required at runtime
- `docs` — full markdown for sr-docs entry + in-app drawer
- `optionsResolvers` — optional list of `{ field, source }` entries describing how `resource-picker` widgets fetch their options at runtime
- `oauthSpec` — optional, only for OAuth integrations: `{ authorizationUrl, tokenUrl, scopes, clientIdEnvVar, clientSecretEnvVar }`

### 4.2 `uiSchema` — declarative panel description

Drives generation of the real Svelte panel. Backwards-compatible: existing nodes can keep using `basicConfig`, which is treated as a thin alias for a flat `uiSchema`. New curated nodes always emit `uiSchema`.

Top-level shape:

```ts
{
  layout: 'single' | 'two-column' | 'tabs',
  sections: [
    {
      title: 'Authentication',
      intro?: 'markdown',
      showWhen?: condition,
      fields: [...]
    },
    ...
  ],
  banners?: [
    { kind: 'credential-status', credentialField: 'credential' }
  ],
  actions?: [
    { kind: 'test-connection', label: 'Test credential',
      endpoint: '/api/integrations/test/[integrationType]' }
  ]
}
```

Field widget types in v1:

- Basics: `string`, `textarea`, `dropdown`, `toggle`, `number`, `datetime`
- `credential-picker` — pulls from `integrationCredentials` filtered by `integrationType`. Includes a "+ New" button that opens an inline credential form.
- `resource-picker` — async dropdown. Calls `/api/integrations/options/[integrationType]/[fieldName]?credentialId=...` at render time. Generic endpoint, dispatches to the per-integration `optionsResolvers` defined on the node spec.
- `template-string` — string input with a chip-rail of available `{{upstream}}` variables
- `key-value-list` — pair editor
- `code-block` — syntax-highlighted text area (e.g. for JSON Schema fields)
- `enum-with-icons` — like dropdown but each option has an icon

Conditionals: `showWhen` accepts simple equality / `in` / `not-in` predicates against other field values. Composability via `allOf` / `anyOf`.

Codegen target: a Svelte component that mirrors the structure of `GmailSendPanel.svelte` — top-level `<script>` for state + props (`config`, `onChange`, `definition`, `nodeId`, `workflowId`, `upstreamFields`), then markup grouped by section. All standard widgets are extracted as shared components in `src/lib/canvas/nodes/panels/widgets/` so the generated panel files stay readable.

### 4.3 Generic Credentials Store

New Drizzle table `integrationCredentials`:

| column | type | notes |
|---|---|---|
| `id` | uuid | pk |
| `integrationType` | text | e.g. `'apple-calendar'`, `'trello'` |
| `label` | text | user-given, for the picker UI |
| `kind` | text | `'apikey' \| 'basic' \| 'oauth2'` |
| `payload` | text | AES-256-GCM-encrypted JSON; shape depends on `kind` |
| `metadata` | jsonb | non-secret config (CalDAV server URL, OAuth callback URL override, …) |
| `createdAt` | timestamptz | |
| `updatedAt` | timestamptz | |

Encryption: single new env var `INTEGRATION_CREDENTIALS_KEY` (32-byte hex). Helper `getCredential(id)` decrypts on demand. For `oauth2`, an `ensureFreshAccessToken(id)` helper auto-refreshes when `expiresAt` is past, using `tokenUrl` from the matching `integrationOauthConfigs` row.

OAuth metadata table `integrationOauthConfigs` (one row per `integrationType` that uses OAuth):

| column | type |
|---|---|
| `integrationType` | text (pk) |
| `authorizationUrl` | text |
| `tokenUrl` | text |
| `defaultScopes` | text[] |
| `clientIdEnvVar` | text |
| `clientSecretEnvVar` | text |

Generic OAuth callback route: `/api/integrations/oauth/[integrationType]/callback`. Validates state, exchanges code for tokens, writes/updates the matching `integrationCredentials` row.

Admin UI: `/admin/integrations` — lists credentials grouped by `integrationType`, supports add / edit / delete. Curate links to it from the credential-create inline form.

### 4.4 Curate Sessions Persistence

New Drizzle table `curateSessions`:

| column | type | notes |
|---|---|---|
| `id` | uuid | pk |
| `slug` | text | url-safe |
| `status` | text | `'scoping' \| 'discovering' \| 'awaiting-approval' \| 'generating' \| 'live-testing' \| 'awaiting-promotion' \| 'promoting' \| 'promoted' \| 'aborted' \| 'error'` |
| `goal` | text | one-line outcome |
| `proposal` | jsonb | the structured proposal card |
| `nodeSpec` | jsonb | the canonical node spec |
| `worktreePath` | text | absolute path on homeserv |
| `branchName` | text | `curate/<type>-<sessionId>` |
| `devServerPort` | int | allocated port |
| `iterationLog` | jsonb | array of test-run results + redirects |
| `errorTrace` | text | last error if `status='error'` |
| `createdAt`, `updatedAt`, `promotedAt` | timestamptz | |

### 4.5 Discovery Toolkit

The discovery phase has access to:

- `web.search`, `web.fetch` — generic research
- `context7.resolve` + `context7.queryDocs` — current library/SDK docs
- `repo.readNodes` — reads `src/lib/workflows/nodes/` and `src/lib/canvas/nodes/panels/` for pattern reuse
- `repo.readSrDocs` — reads the sr-docs corpus
- `repo.readPackageJson` — checks already-installed deps to bias toward reuse
- `sandbox.probe(integrationType, scriptSource, credentialId)` — opt-in, gated. Runs short read-only fetch snippets in `jkai-sandbox`. Mutating probes require user approval per call.

The orchestrator's discovery system prompt explicitly forbids the "fall back to `http-request`" behaviour. Discovery must produce a node-specific design or end the session with "this isn't possible".

### 4.6 Worktree Management

- Worktrees live under `~/.curate-sessions/<sessionId>/`. Naming uses session id, not type, to allow concurrent sessions on the same target type without collision.
- Branch naming: `curate/<type>-<sessionId>`.
- A **template worktree** at `~/.curate-sessions/.template/` is maintained with `node_modules` pre-installed. New sessions hard-link `node_modules` from the template into the new worktree to avoid 30s+ cold installs. The template gets refreshed (full `npm install`) whenever `package.json` or `package-lock.json` on `main` changes.
- Port pool: 5180-5199 (20 concurrent sessions). Allocator persists in `curateSessions.devServerPort`. Released on session end.
- A **stale-session reaper** runs daily and prunes worktrees + branches for sessions that have been in non-terminal states for more than 14 days.

### 4.7 Documentation Generation

- The `docs` field on the canonical spec is the single source of truth.
- Generated `sr-docs` markdown file at promotion time: structure follows the existing nodes-*.md pages in sr-docs, with sections "When to use", "Configuration", "Output", "Examples".
- In-app drawer: a new collapsible "Docs" section in the canvas config menu, available on every node that has a `docs` field. Renders the same markdown.
- Drift check: the post-promotion verify step compares the live `docs` field on the registered node against the file in sr-docs and warns on mismatch (in case someone hand-edits one without the other).

## 6. Apple Calendar Worked Example

(Condensed — full trace in §3 of the brainstorming dialogue and reproduced as a test scenario for the implementation plan.)

- Scope: read + write iCloud calendars, single account
- Discovery: rejects EventKit (macOS-only); picks CalDAV (RFC 4791) at `https://caldav.icloud.com`. Auth via app-specific password. Already-installed `xml2js` ✓ would work but discovery selects `tsdav` for cleaner CalDAV semantics (handles `REPORT`/`PROPFIND`, recurring expansion, ETag matching). The new `tsdav` dep is added to `package.json` inside the worktree; if the session is aborted, the worktree (and the dep change) is thrown away.
- Proposal: node `apple-calendar`, category `integrations`, basicConfig replaced by full `uiSchema` with sections "Connection" / "Operation" / conditional "Date range" / conditional "Event details" / conditional "Target event"; calendar field uses `resource-picker` with a CalDAV principal-lookup resolver
- Generate: worktree at `~/.curate-sessions/<id>/`, branch `curate/apple-calendar-<id>`, dev server on `homeserv:5180`, credential prompt → `integrationCredentials` row with kind=`basic`
- Live test: 3 test cases (list / create / delete) run against real iCloud; user opens `homeserv:5180/jkai/canvas`, plays with the real `AppleCalendarPanel.svelte`, confirms
- Promote: merge → push → `scripts/deploy.sh` → verify on prod → cleanup

## 7. Error Handling & Failure Modes

- **Dirty main at session start**: refuse to create worktree; ask user to stash/commit/abort their other work
- **`npm install` failure**: stop in Generate, leave worktree intact, surface stderr in chat, offer Retry / Edit `package.json` / Abort
- **`tsc` failure post-iteration**: pause live-test, surface diagnostics; user can redirect ("fix the type error") or abort
- **Test-case failure**: not an error — feeds back into the live-test loop. After 5 consecutive failures curate stops asking and surfaces options
- **Dev server crash**: detected via heartbeat; curate offers restart. Repeated crashes pause the session and show logs
- **Promotion git conflict** (main moved): rebase the curate branch; if rebase has conflicts (rare for new node files), abort promotion and surface the diff
- **Deploy failure**: pause at the deploy step; user can retry the deploy script or roll back (`git revert` the merge commit, push, redeploy)
- **Verify-live failure** (registry doesn't show new node post-deploy): surface, offer rollback or "investigate manually". Don't auto-rollback because the cause is usually a deployment race the user will want to inspect
- **OAuth callback timeout** (during credential setup): credential row stays in `pending` state; user can retry the OAuth flow

## 8. Testing Strategy

- **Unit tests**:
  - `uiSchema` validator + Svelte-codegen (golden-file: feed in known schemas, assert on emitted Svelte source)
  - Canonical node spec → repo-files emitter (golden-file)
  - Generic credentials encrypt / decrypt + OAuth refresh helper
  - Conditional `showWhen` evaluator
- **Integration tests** (against a throwaway worktree on a test branch):
  - Full Generate → npm install → tsc → dev server up → tear down
  - Promotion pipeline against a fixture node, including merge + sr-docs symmetric merge, on a sandbox repo clone
- **End-to-end**: a recurring CI job that runs a fixture curate session ("Curate a node that hits httpbin.org") to catch regressions in the discovery → generate → live-test → promote loop. No real prod deploy in CI.

## 9. Out of Scope / Future Work

- **Re-curation / editing existing nodes** — v1 only creates new node types. v2 might support "open this curated node in a curate session" (load existing repo files into a worktree, allow iteration).
- **Curate from the VPS UI** — v1 is homeserv-only. Production reachability is via deploy after promotion.
- **Deep `optionsResolvers` editor** — for v1, resource-picker resolvers are hand-tuned by the discovery phase. A future iteration could let users edit them post-promotion.
- **Cross-node refactors** — curate doesn't refactor existing nodes; only adds new ones.
- **Multi-tenancy / sharing** — single-user assumption.
- **Auto-merge of upstream `main` during long-lived sessions** — for now sessions assume `main` is stable; conflicts at promotion are handled but not preempted.

---

## 10. Open Questions

- **Sr-docs symmetric merge ergonomics**: writing into the sr-docs repo from curate sessions while maintaining its own git history. Plan: each curate session creates a symmetric branch in sr-docs, gets merged at promotion. Worth confirming during implementation that this doesn't fight existing sr-docs deploy timing.
- **Dev-server warmup time** even with template-worktree node_modules: needs measurement during phase 1 implementation. If still >10s, user-perceived "Generate" latency may need a progress UI more elaborate than the streaming chat.
- **Generic OAuth client credentials** (`clientIdEnvVar` / `clientSecretEnvVar`): for some integrations (Trello, Notion) the user must register an OAuth app first. Curate's discovery should produce a "you'll need to do these one-off setup steps before I can generate this node" pre-checklist when the integration requires it.
